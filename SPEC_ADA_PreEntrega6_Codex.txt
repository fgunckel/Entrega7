## 2. Objetivo del producto

ADA es un asistente de decisiones de arquitectura de software. Recibe un escenario técnico, recupera evidencia de un corpus local, compara alternativas con una matriz de criterios ponderados y genera una recomendación final trazable.

Escenario de demostración sugerido: decidir si una API .NET debe permanecer como monolito, evolucionar a monolito modular o migrar a microservicios. El usuario debe poder aportar restricciones como tamaño del equipo, complejidad operativa, necesidad de despliegues independientes, escalabilidad y presupuesto.

El sistema no debe presentar opiniones del LLM como hechos verificados. Las afirmaciones basadas en el corpus deben incluir referencias a sus fuentes; el análisis numérico debe calcularse con Python determinístico.

## 3. Requisitos obligatorios de la Pre-entrega 6

La solución debe demostrar:
- Topología jerárquica con un nodo `Supervisor` que decide dinámicamente el siguiente nodo.
- Al menos dos especialistas funcionales: `Researcher` (búsqueda/investigación) y `Analyst` (análisis/cómputo).

- Grafo `StateGraph` con aristas condicionales y finalización explícita.
- Validación determinística con reglas de Python/Pydantic.
- Manejo de errores de validación: reparación acotada con mensaje de error concreto y, si no se resuelve, salida de revisión humana o resultado no aprobado.
- Aislamiento de escritura: cada agente escribe únicamente en su propio campo de salida.
- Límite de pasos/reintentos para impedir bucles infinitos.
- Síntesis final que integre investigación, análisis y validación.
- Tests del camino normal y del camino de fallo.
- README con explicación de la topología y diagrama Mermaid del grafo.

Criterios de evaluación a priorizar: arquitectura del grafo y supervisor (35%), especialización/estado/herramientas funcionales (45%), documentación y diagrama (20%).

## 4. Alcance mínimo (MVP)

### Incluido
1. Recuperación local híbrida: BM25 + embeddings locales + Reciprocal Rank Fusion (RRF).
2. Corpus de documentos técnicos versionados dentro de `data/corpus/`.
3. Agente `Researcher` que consulta el recuperador y devuelve evidencias con fuente.
4. Agente `Analyst` que compara alternativas con criterios y pesos y usa el módulo determinístico de scoring existente.
5. `Supervisor` que selecciona el próximo nodo mediante salida estructurada de LLM, usando LangGraph y el proveedor Groq configurado.
6. Nodo `Validator` determinístico que comprueba contratos, pesos, puntajes, referencias y campos requeridos.
7. Nodo `Synthesizer` que genera el informe final en formato estructurado.
8. Límite de pasos y reparaciones, con salida controlada cuando no se pueda validar.
9. CLI simple para ejecutar una decisión de ejemplo desde terminal.
10. Tests unitarios y tests del grafo con LLM/retriever simulados para no requerir red ni claves en CI.
11. README de instalación, configuración, arquitectura, ejemplo de ejecución y limitaciones.

### Fuera de alcance
- Interfaz web o frontend.
- Pinecone, Chroma, base de datos, servicios cloud o infraestructura desplegada.
- Agentes autónomos ilimitados o ciclos de reflexión sin condición de parada.
- Reranking, observabilidad externa, colas, autenticación o despliegue productivo.
- Hacer llamadas a Groq en cada test.
- Añadir complejidad de producción que no ayude a demostrar los objetivos de la entrega.

## 6. Arquitectura objetivo

```mermaid
flowchart TD
    START([START]) --> SUP[Supervisor]
    SUP -->|needs evidence| RES[Researcher]
    SUP -->|needs comparison| ANA[Analyst]
    SUP -->|ready to verify| VAL[Validator]
    SUP -->|validated| SYN[Synthesizer]
    SUP -->|step/retry limit or unresolved error| HITL[Human review / limited result]
    RES --> SUP
    ANA --> SUP
    VAL -->|valid| SYN
    VAL -->|repairable and retries remain| SUP
    VAL -->|invalid and retries exhausted| HITL
    SYN --> END([END])
    HITL --> END
```

El Supervisor coordina; no realiza el trabajo especializado. Usa una salida estructurada (por ejemplo, `RoutingDecision`) y aristas condicionales. Cada worker devuelve únicamente su artefacto y los metadatos de ejecución necesarios.

No se exige que el LLM use todas las rutas en cada ejecución. El flujo de demostración debe recorrer Supervisor → Researcher → Supervisor → Analyst → Supervisor → Validator → Synthesizer → END, o una variante equivalente bien documentada.

Los artefactos deben ser Pydantic y tener contratos explícitos. Los puntajes de confianza deben estar en `[0, 1]`; los puntajes de criterios en la escala definida por los modelos existentes; los pesos deben sumar 1 con tolerancia pequeña. No dupliques el mismo dato en varios campos si no es necesario.

No pases todo el historial de mensajes a cada especialista por defecto. Pasá la solicitud y el contexto mínimo requerido.

## 9. Especialistas y responsabilidades

### Researcher
- Recibe una pregunta de investigación derivada de la solicitud.
- Usa `HybridRetriever` para recuperar hasta cinco evidencias.
- Devuelve un `ResearchArtifact` validado con resumen, hallazgos, confianza y fuentes.
- Cada afirmación respaldada debe apuntar a uno o más IDs de fuente recuperada.
- Si no hay evidencia suficiente, debe indicarlo explícitamente; no inventar fuentes.

### Analyst
- Compara alternativas predefinidas pertinentes: monolito, monolito modular y microservicios (permitir ajustar si el escenario lo justifica).
- Usa criterios configurables con pesos que sumen 1.
- Usa `calculate_weighted_score` y `rank_alternatives` ya existentes; no delegar aritmética al LLM.
- El LLM puede proponer racionales/puntajes por criterio con evidencia, pero Python valida el esquema y calcula los totales.
- Devuelve `AnalysisArtifact` con puntuaciones, explicación de trade-offs, ranking y supuestos.

### Validator
- Nodo determinístico, no otro LLM.
- Comprueba Pydantic, completitud, unicidad de IDs, pesos, rangos de puntajes, existencia de referencias citadas dentro de las evidencias recuperadas y coherencia entre puntuación y scoring calculado.
- Devuelve errores concretos y accionables.
- Si es reparable, permite un máximo de dos intentos de corrección; al agotarse, marca `requires_human_review` o devuelve un resultado no aprobado con los errores visibles.

### Synthesizer
- Genera un informe legible que incluya contexto, alternativas, tabla de criterios ponderados, recomendación, riesgos, supuestos, evidencias/citas y nivel de confianza.
- No debe inventar hechos ni fuentes; debe basarse en artefactos validados.
- Si el validador no aprobó, no presentar la recomendación como definitiva.

### Supervisor
- Decide la siguiente tarea usando salida estructurada.
- No modifica los artefactos de los especialistas.
- Debe tener instrucciones/prompt versionados en el repositorio.
- Impone un máximo de pasos configurable (por defecto 8) y un máximo de reparaciones (por defecto 2).
- Si el modelo falla, devuelve una ruta segura y un mensaje de error controlado; no entrar en bucle.
